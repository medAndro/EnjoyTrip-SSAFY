# 2인 역할 분담과 180분 진행표

- A 이름: __________ / 관광지 조회 + 여행 계획
- B 이름: __________ / 회원 + Hotplace

두 사람 모두 HTML/CSS/JS를 다룬다. 디자인 담당/JS 담당으로 나누지 않는다. AI가 제공한 공통 UI를 활용하여 기능 연결에 시간을 집중한다. AI는 학습 멘토이며 두 명의 구현 인원에 포함하지 않는다.

## 파일 담당

| A 단독 수정 | B 단독 수정 |
| --- | --- |
| attractions.html, css/attractions.css, js/attractions.js | signup.html, login.html, mypage.html, css/members.css, js/members.js |
| plans.html, css/plans.css, js/plans.js | hotplaces.html, css/hotplaces.css, js/hotplaces.js |
| js/data.js | js/storage.js, js/session.js, js/common.js |

공통 CSS, config.js, 지도/사진 helper, 메인 화면은 처음 3시간에는 최대한 그대로 쓴다. 공통 계약 변경은 서로 알린 뒤 한 사람이 반영한다. 공통 HTML 메뉴 구조를 바꿀 때도 상대가 해당 파일을 수정 중인지 먼저 확인한다.

## 180분 병렬 진행

| 시간 | A | B | 확인 지점 |
| --- | --- | --- | --- |
| 0~15분 | 화면/관광지 형식 읽기, JSON fetch 시작 | 화면/Storage 형식 읽기, 저장 함수 시작 | 파일 실행, 공통 키 확인 |
| 15~75분 | 목록·필터·상세, 지도 helper 연결 | 회원가입·로그인·세션·정보 수정·탈퇴·재설정 | 필수 흐름의 최소 성공 동작 |
| 75~130분 | 관광지 초안 전달, 일정 순서·경비·저장/복원 | 사진 이벤트·미리보기·등록·목록·지도/복원 | 두 추가 기능 기본 동작 |
| 130~155분 | 회원별 계획 분리, 로그인/탈퇴 연결 | 공통 메뉴·로그아웃, 소유자 분리 | 두 회원으로 통합 |
| 155~180분 | 함께 오류/빈 결과/새로고침 점검 | 함께 캡처·README 정리 | 남은 TODO를 숨기지 않음 |

3시간은 목표 분량이며 속도를 보장하는 약속은 아니다. 앞 단계가 지연되면 디자인 변경/키워드/일정 시간 입력/Hotplace 삭제부터 줄인다. 회원 관리·유형 필터·저장/복원의 핵심을 먼저 완성한다. API 가입과 키 발급은 가능하면 시작 전에 한다.

## A — 작은 작업 순서

- [ ] `data.js`: config의 URL을 fetch하고 배열을 반환한다. HTTP 실패를 확인한다.
- [ ] `attractions.js`: 샘플 카드를 제거하고 받은 배열을 목록으로 만든다.
- [ ] 검색 submit에서 지역·유형으로 filter하고 0건을 표시한다. 키워드는 여유가 있을 때.
- [ ] 상세 버튼에서 id로 항목을 찾고 dialog 내용/닫기 이벤트를 연결한다.
- [ ] 지도 helper를 초기화하고 검색 결과를 전달한다. 키가 없으면 목록을 계속 사용할 수 있다.
- [ ] 상세의 일정 추가에서 관광지 ID를 세션 초안에 저장한다.
- [ ] `plans.js`: 현재 회원의 저장 계획 또는 초안을 불러온다.
- [ ] 항목 제거/위·아래 순서 변경/날짜·경비·메모 입력, 저장과 복원을 연결한다.

A의 수도코드:

```text
JSON 요청 → 응답 확인 → 배열
검색 입력 → filter → 목록 생성 → 지도에 같은 배열 전달
상세 클릭 → ID로 조회 → dialog 표시
일정 추가 → ID 초안 → 계획 화면
방문 배열 편집 → 합계/기간 확인 → ownerId 포함 저장
```

## B — 작은 작업 순서

- [ ] `storage.js`: JSON read/write 두 함수를 구현한다. 없으면 기본값, 손상/저장 실패면 오류.
- [ ] `session.js`: 회원 찾기/세션 설정/해제 세 함수를 구현한다.
- [ ] 가입 검증과 중복 ID 검사 후 회원 저장.
- [ ] 로그인 대조 후 세션 ID 저장, 로그아웃 시 세션/계획 초안 삭제.
- [ ] 내 정보 표시·닉네임/이메일 수정·탈퇴 연결.
- [ ] ID+샘플 이메일 확인 후 새 데모 비밀번호 설정.
- [ ] 파일 change 이벤트에서 사진 helper를 호출하고 img.src로 미리보기.
- [ ] Hotplace 폼 검증 후 ownerId/사진/좌표/방문일/설명 저장.
- [ ] 자신의 목록을 렌더링하고 지도 helper에 좌표를 전달.

B의 수도코드:

```text
가입 폼 → 검증/중복 확인 → 회원 배열 저장
로그인 폼 → 계정 대조 → 세션 ID → 메뉴 표시
파일 선택 → 사진 helper 완료 대기 → 미리보기
등록 폼 → 검증 → ownerId 포함 저장 → 목록/지도 갱신
```

## 연결 약속과 대기 줄이기

- B는 처음에 readJSON/writeJSON/getCurrentUser를 먼저 만들어 A에게 알려 준다.
- A는 B 완료 전까지 샘플 배열을 표시하고 일정 편집을 연습한다. 임시 회원 ID는 통합 전에 제거한다.
- 관광지 ID와 Storage 키는 DATA_CONTRACT.md를 따른다.
- 탈퇴는 B가 회원 배열에서 제거한 뒤 계획/Hotplace 배열도 ownerId로 정리한다. 공통 저장 함수를 사용하면 다른 페이지 모듈 import가 필요 없다.
- A의 일정 파일과 B의 Hotplace 파일을 서로 직접 수정하지 않고 오류를 알려 준다.
- 두 사람이 각자 마무리되면 서로의 화면에서 새로고침과 다른 계정 전환을 시연한다.

## AI에게 요청하는 방식

우선 수도코드·필요한 API 이름·디버깅 힌트를 요청한다. 요청 예: “이 submit 이벤트에서 배열은 바뀌는데 저장이 안 된다. 원인을 찾을 확인 순서를 알려 줘.” 핵심 CRUD의 완성 코드를 대신 작성하게 하지 않는다.

각자 한 번씩 설명할 질문:

- A: await 전후의 실행 순서, filter 결과와 DOM의 관계, 일정 순서가 어디에 저장되는가?
- B: JSON.stringify/parse가 필요한 이유, 세션과 영속 저장의 차이, 사진 준비 완료 전에 저장하면 왜 문제가 생기는가?
